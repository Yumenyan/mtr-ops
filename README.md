# MTR 運行監視・車両管理システム (mtrops)

MTRmod 3.2.2-hotfix-1 / Minecraft 1.19.2 / Fabric 用。サーバーが車庫・編成・車両番号の台帳を持ち、
クライアントがローカル HTTP API (127.0.0.1) とWebアプリを提供します。

- `mod/` Fabricモッド本体 (`core/` は純Javaで単体テスト済み、`adapter/` がMTR依存部)
- `web/` Webアプリ(jarに同梱され同じポートから配信。外部CDN・フォント不使用)
- `core-test/` 単体テスト(`run.sh`)と、MODなしでWebを試せる疑似サーバー(`dev-server.sh 8765`)
- `docs/` 優先度表(`PRIORITY.md`)、画面スクリーンショット

## ビルド
1. `mod/libs/` に MTR-fabric-1.19.2-3.2.2-hotfix-1.jar を置く
2. Gradle **8.6以上**(推奨 8.8)とJDK 17で `cd mod && gradle build`(IntelliJは Settings→Gradle の Gradle JVM を17、Gradleを8.8に。Loom 1.6使用。古いLoom 1.1は Gradle 8 で `SelfResolvingDependency` エラーになります)。 → `build/libs/` のjarを `mods/` へ(サーバー・クライアント両方、Fabric API必須)

## 使い方
- ワールドに入ると自動でローカルHTTPが起動。チャットで `/mtrops web` でブラウザが開く(`/mtrops url` `/mtrops status`)
- `/mtrops` で車庫・編成の管理GUI(キー割り当ても可能)。設定は `config/mtrops.json`
- MODなしで画面確認: `core-test/dev-server.sh 8765` → http://127.0.0.1:8765/

## ローカルAPI(外部プロジェクト向け)
127.0.0.1 の HTTP で JSON を返します(読み取り専用)。駅間距離・線路の線形は次のとおりです。
- `GET /api/geometry` 駅間ごとの距離(ブロック)と線形(折れ線 `[x,y,z]`)。`?from=駅ID&to=駅ID` で絞り込み
- `GET /api/sections` 駅間距離のみ(`?points=1` で線形つき)
- `GET /api/routes/{路線ID}` 路線の駅順・駅間距離・累積距離・線形(`?points=0` で線形なし)
- `GET /api/distance?from=駅ID&to=駅ID[&route=路線ID]` 2駅間の線路沿い距離。`route` 指定でその路線の停車順に沿って合計、無指定は区間グラフの最短経路
- 線形は、サーバーが走行中の列車の経路(PathData)から少しずつ集めます(約5秒おきに3列車ずつ)。まだ列車が走っていない区間は `"measured":false` で、駅の座標の直線距離で補います。
- `GET /api/schedule/{駅}` 駅の時刻表(2時間先まで、`?hours=` で変更)。駅はID・英名・和名で指定(例 `/api/schedule/nagaumi`)。走行中の列車は到着予想、まだ出庫していない列車は車庫の出庫時刻 + 所要時間から推定、カスタムダイヤは時刻表
- `GET /api/runtimes` 駅間ごとの所要時間(MTRの理論値の走行・停車、実測の平均、見込み)。`/api/sections` `/api/routes/{id}` にも `runtime` が付きます
- `GET /api/rails`(`/api/geometry/rails`)レール1本ごとの形と種別(`mode`=train/boat/cable_car/airplane、`type`=MTRのRailType、`role`=line/platform/siding/turn_back 等)。`/api/geometry` の区間にも `mode` と `parts`(種別ごとの区切り)が付きます
- 列車の `etas`(到着予想)は折り返し後の路線も含み、既定で20分先まで(`?etaHorizon=秒`)。MTRの発車標と同じ計算を、駅間ごとの実績で補正しています
- 停車しない列車(通過)も、`/api/schedule/駅` の `"pass":true` と、列車の `etas` の `pass` で取れます(発車標からは `passCount` などのメソッド)
- `GET /api/dia` ダイヤ編成ツールの設定・時刻表・詰まり/待避の診断(読み取りのみ)
- そのほか `/api/live` `/api/trains` `/api/stations` など。ID はすべて文字列です。

## 車番(編成番号)の付け方
- `/mtrops` のGUIで、車庫線ごとに「車番の範囲」(トプナン〜ラスナンの2つ。例: 1001 〜 1100)を入れて保存すると、その車庫線から出庫した列車へ空いている若い番号が自動で付きます(1001, 1002…)。番号はワールドに保存され、再起動後も同じ列車は同じ番号です。
- 番号は表の編成番号欄で直接書き換えられます(範囲外、または同じ車種(mtr_custom_resources.json の車両ID)で重複する番号は保存時に弾かれます。車種が違えば同じ番号でも登録できます)。GUIには車庫・車庫線に登録されている車両名が表示されます。
- 車庫ごとに「除外番号」(例 `4, 9, 1013-1019`)を設定すると、自動採番と[＋追加]がその番号を飛ばします。車番範囲の横の[ランダム]をONにすると、出庫のたびに範囲内の空き番号(使用中・他で登録済み・除外を除く)から無作為に採番します(OFFは若い番号から)。系列を空にすると、MTRのリソース(mtr_custom_resources.json)に載っている車両名が使われます。
- 自動採番は、設定 `skipNumberEndings`(既定は numberdisp.js の忌み番号リストと同じ)に末尾3桁が一致する番号を飛ばします。手動で付ける番号には適用しません。
- 範囲が満杯、または未設定の列車は「番号未設定」と表示されます。

## 他アドオン(NTE/Rhinoスクリプト)から車番を読む
`jp.mtrops.api.MtrOpsApi`(クライアント側)が公開メソッドです。発車標の `ScheduleEntry` ごとに遅れ・編成番号・車種を取る `entryDelaySec` / `entryNumber` / `entryTypeId` / `entryTypeName` も使えます。`docs/scripts/numberdisp.js` は、既存の車番ロジックをこのAPI呼び出しに置き換えた版です。詳細は `docs/SCRIPT_API.md`。

## 駅番号
駅名に `[AA01]`(ハイフン付き `[AA-01]` も可)があり、かつ路線名の `( )` 内の英字(例 `(AAAC)` → AA / AC)にその英字が含まれるときだけ、丸バッジに駅番号を出します。該当しなければ何も出しません。

## 既知の制約
- 発車標(ScheduleEntry)のフィールド名と `ClientData`(DATA_CACHE / SCHEDULES_FOR_PLATFORM)は、MTRのソースを手元で確認できなかったためリフレクションで読んでいます。読めない場合は該当なし(空文字/0)になるだけで落ちませんが、ゲーム内での動作確認が必要です。
- MOD層は `core-test/mod-check.sh` で、外部クラスの代用品(スタブ)に対する型チェックだけ行えます(MTRの部分はソースから写した定義)。本物のjarでのビルドではありません。
- **MOD層(adapter/server/client/GUI/gradle)はこの環境でコンパイルできていません**(Maven等が遮断)。純Javaの`core`のみ71テスト合格。初回ビルドでの微修正が必要な可能性があります。
- MTR内部はリフレクションで参照。MTRバージョンが違うと起動時 selfCheck が警告します。
- 遅延は再起動直後は0から。車両ごとの任意番号はGUIでは未編集(編成ID-Nで自動採番)。
- 専用サーバー側HTTPは未実装(クライアント側のみ)。

## ダイヤ編成ツール(発車時刻の定義)
アイテム「ダイヤ編成ツール」(MTRの鉄道ダッシュボード + 時計でクラフト)で、路線のホームごとの発車時刻をゲーム内で決めます。MTRの停車時間に依存せず、種別ごとの発車時刻・発車時刻単位の待避を実現し、詰まる所・待避できる所をリアルタイムに案内します。詳しくは `docs/CUSTOM_DIA.md`。

## Webアプリ(v2)
東京メトロmy!アプリをPC向けにしたデザインです。ホーム(路線シンボルの選択 → 運行状況 → 横型の列車位置)、路線一覧、車両、スタック調査、設定。
- 同じ路線名(括弧書きを除く)の系統は自動で1本のラインにまとめます。
- 列車位置は駅間を広く取り、同じ区間に列車が詰まっても縦の段に積んで全列車を表示します。
- 列車詳細は、通過済みの駅(薄く)→ 編成(駅間の実際の位置)→ これから停まる駅(次の駅/まもなく)の順です。
- 路線リストは左に固定表示(文字なしの路線色の丸)。更新では並びも選択もスクロールも動きません。同じ路線名・同じナンバリングの路線は1つにまとめます。
- 列車詳細には各駅の到着予想(ダイヤ上の残り時間から計算した現実の時刻(端末の時計))を出し、停車中は駅名の横に号車一覧を出します。
- 異常タブ・地図タブは廃止しました(地図は別プロジェクトへ移植予定)。

## スタック調査タブ(ゴースト疑い)

MTR 3.2.2-hotfix-1 のソースを読んで定義した「動かないまま閉塞を塞ぎ続ける車両」の疑いを一覧にします。
- 停止固着: `nextStoppingIndex >= path.size()`(MTRが毎tick何もしない)。
- 経路・距離表なし: 経路が空、または距離表が不足していて位置が算出できない(座標は車庫線の位置)。
5秒以上続くと「疑い確定」になります。座標の移動コマンドと列車IDをコピーできます。
確定ではなく疑いです。実物と照らして基準を調整してください。


## 車番の構成 (v5)

- トプナン/ラスナンの欄には「モハE233-1001」「TX-1000」のように数字以外の文字も入れられます。数字部分だけが増減し、前後の文字は編成番号にそのまま付きます。
- 各車の車番(「各車」ボタンで切替):
  - 編成-N: 従来どおり(例: TX-1001-1)
  - 連番: 1001～1008, 1009～1016 のように両数ごとに区切る
  - 桁置換: 1101,1201,…のように号車ごとに指定の桁(「桁」ボタン)を変える
- GUIにプレビュー行があり、実際に出る車番を確認できます。
- プロトコル/保存形式が v5 になりました。サーバーとクライアントのMODは同時に更新してください。
- スクリプト側は mtrops 導入を自動検出して旧/新を切替(ClientConfig不要) → docs/CAR_NUMBER_SCRIPT.md
- MTRのロープウェイ(CABLE_CAR)は「運行情報と列車情報の不一致」の対象外です。

## キーバインド
- `K`: 車庫・編成管理GUIを開く / `L`: 運行情報Webをブラウザで開く(どちらも設定 → 操作 → MTR Ops で変更可)。
- 開くだけなら権限は不要です(読み取り専用)。編成の変更・保存は、サーバー側で権限(`requireOpToEdit` が有効ならOP権限レベル2、そうでなければMTRの編集権限)を検査します。

## 補足 (v5.1)
- 連番/桁置換の編成を自動登録・ランダム採番するとき、同じ車種の他編成の表示番号(各車の車番)と被る候補は飛ばします(両数が違う編成が混在しても被りません)。
- 各車の車番の既定表記は「編成番号-N」(「号車」は付けません)。
- Webの列車位置(路線図・地図)は、列車の実座標を駅間に射影して決めます。快速の通過駅を挟む区間でも、実際の位置に表示されます。
